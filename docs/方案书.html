摘要

急先锋面向园区、企业、学校、医院、社区和应急演练服务机构，解决“有资源但不会快速形成可执行调度方案”“方案生成了却没有独立核验”“现场条件变化后不能及时重算”等问题。平台把复杂调度任务拆分为需求研判、资源匹配、独立核验和方案交付四个可配置智能体，通过可视化工作流完成并行理解、条件判断、退回重算和人工审批，并以库存快照、路网规则和 RAG 证据链保证结果可追溯。

平台并不把大模型当作唯一计算器。库存数量、车辆载重、路线时效、需求覆盖和硬性约束由确定性工具计算；LLM/AgentArts 承担需求理解、策略解释、方案组织和人机交互；独立核验智能体依据原始数据和规则引擎对候选方案进行否决或放行；方案生成智能体只能接收结构化问题代码、证据和修正要求，不能读取核验智能体的内部推理。由此形成“生成—核验—退回—重算—再核验—人工审批—交付”的 PDCA 闭环。

当前原型已实现物资库、库存上传与版本快照、场景配置、三套多目标方案生成、道路封闭拦截、自动改用备用通道、双轮核验、实时 Agent 事件、人工审批和报告导出。固定基准场景中，第一轮 3 套方案全部被独立核验拦截，发现 7 类硬阻断；第二轮重算后 3 套方案通过，需求覆盖率 100%，核验评分由 0 提升至 100，重复计算结果一致，纯规划计算耗时约 1 毫秒。系统还通过测试用例验证了完整流程和 API 主链路。

一、选题背景与场景需求

1.1 真实问题

应急物资调度看似只是“把物资从仓库送到安置点”，实际包含需求研判、物资匹配、路线选择、车辆载重、库存锁定、优先级分配、时效判断、道路封闭、人工审批和过程留痕等多个耦合环节。任何单一环节判断错误，都可能造成物资错配、车辆空驶、关键物资延迟或方案无法执行。

传统人工方式主要依赖表格、电话和会议协调，存在以下痛点：

  1. 物资名称和单位不统一。同一种物资可能出现“水”“矿泉水”“瓶装水”等多个名称，箱、瓶、件混用后无法准确计算。
  2. 仓库和库存信息更新不及时。方案生成后若库存被其他任务占用，原方案可能失效。
  3. 路线和时效依赖经验。主通道封闭、桥涵限重、车辆载重不足等问题往往在执行前才被发现。
  4. 方案缺少独立复核。生成人员同时也是判断人员，容易形成确认偏差。
  5. 现场变化快，但重新计算依赖人工，难以在短时间内形成多套备选方案。
  6. 过程不可追溯。评审或复盘时难以说明为什么选择了某个仓库、路线和车辆。

1.2 赛题契合性

赛道一强调多智能体协作、工作流编排、动态调度、执行验证和自我循环。急先锋不是一个 Agent 完成一次大模型调用，而是让多个角色围绕同一任务产物协作。需求智能体负责理解，匹配智能体负责组合，核验智能体负责否决，交付智能体负责汇总。每个角色有不同工具权限、记忆范围和禁止事项。工作流中包含并行分支、条件判断、循环重算和人工门控，符合赛题对平台级作品的要求。

1.3 目标用户

第一阶段的用户不是要求接入政府专网的单位，而是能够自行提供资源数据的组织：

  • 工业企业园区和化工园区
  • 学校、医院、大型场馆
  • 物流仓储企业和物业服务企业
  • 社区应急管理站
  • 应急演练服务机构和培训单位
  • 需要编制内部应急预案的中小企业

这些用户可以上传内部物资、仓库、车辆和路线数据，通过演练模式验证预案是否可行。平台不宣称自动发现真实灾害，也不替代现场指挥人员。

1.4 边界定义

本项目的输入是“已经确认的演练事件”或由用户手动录入的事件，不负责自动监测气象、地震、火情或舆情。平台输出是调度草案和辅助决策报告，不输出真实调拨命令。所有真实行动必须经过人工审批，生产落地还需接入授权的应急指挥、仓储、交通和车辆系统。

二、产品定位与核心目标

2.1 产品定位

急先锋是一个数据驱动的应急资源调度推演与预案生成平台。用户可以维护物资主数据、上传库存快照、配置事件和需求，由多智能体生成多套可比较方案，并通过独立核验和反馈循环完成收敛。

2.2 核心目标

  1. 将用户上传的物资资源转化为可计算的库存和运力模型；
  2. 用多目标优化生成时效优先、成本优先和韧性均衡三类方案；
  3. 用确定性规则检查道路、库存、载重、时效和覆盖；
  4. 在核验失败时生成结构化修正要求，而不是简单重试；
  5. 让每一次运行、每一个数字和每一条证据都可追溯；
  6. 在断网或模型不可用时仍能稳定完成核心演示；
  7. 为后续接入真实数据和 AgentArts 工作流保留标准接口。

三、总体架构设计

3.1 分层架构

系统采用五层架构。

第一层是交互层。Vue 3 工作台提供场景配置、物资选择、库存上传、地图态势、Agent 运行轨、多方案对比、核验记录、交付包和人工审批。

第二层是业务 API 层。FastAPI 负责任务创建、库存快照、物资主数据、运行状态、SSE 事件流、审批和报告导出。所有密钥只保存在服务端环境变量，不下发到浏览器。

第三层是编排层。编排控制器负责状态机、并行分支、条件判断、循环上限、超时、错误处理、黑board 产物和事件持久化。

第四层是智能体与工具层。四个 Agent 使用统一输入输出契约；库存、路线、车辆、成本、核验和 RAG 检索均以工具形式注册。Agent 不能直接写数据库，只能调用白名单工具。

第五层是数据层。PostgreSQL 保存物资、仓库、车辆、路线、场景、库存快照、运行记录和 Agent 事件。系统默认通过项目内 PostgreSQL 18 实例运行，同时保留 SQLite 作为离线回退；生产环境可迁移到华为云 RDS for PostgreSQL 或 GaussDB。

3.2 技术选型理由

FastAPI 适合构建清晰、类型化、可测试的异步接口，并能通过 SSE 向 Vue 推送实时事件。Vue 3 组合式 API 便于将工作台拆分为可复用组件。PostgreSQL 支持并发访问、事务、备份恢复和标准 SQL，适合真实 Web 使用；SQLite 仅作为单机断网回退。RAG 使用中文二元组和关键词混合检索，优先保证本地可运行；在真实部署中可替换为 AgentArts 知识库或向量数据库。

3.3 数据流

用户上传库存后，系统解析文件、校验仓库和物资引用、标准化单位和日期，形成不可变库存快照。启动推演时，系统冻结当前数据快照，生成运行编号，调用动态调度器形成任务优先级，再进行需求研判和 RAG 检索。匹配智能体生成候选方案，核验智能体读取原始快照和事件约束进行审查。若存在硬阻断，反馈只包含问题代码、证据和修正要求；匹配智能体据此重新计算。通过后进入人工审批，最后生成交付包和打印报告。

四、Agent 团队设计

4.1 统一契约

四个 Agent 均遵循统一契约：输入包含 run_id、任务描述、输入产物、约束条件和数据范围；输出包含状态、摘要、结构化产物、证据引用、置信度、警告和下一步动作。Agent 不能共享无边界的聊天历史，而是通过版本化黑board交换产物。这样可以避免长上下文污染，也能在审计时还原每个阶段的事实来源。

4.2 需求研判智能体 A01

需求智能体负责把事件、安置点、人口、物资选择和截止时间转化为需求计划。它会读取物资主数据，标准化单位和优先级，按安置人口比例拆分到各安置点，并记录假设。它不能查询库存分配，也不能指定仓库和路线。若物资主数据缺少关键属性，它需要把问题暴露给用户，而不是自行虚构。

4.3 资源匹配智能体 A02

资源匹配智能体读取需求计划、库存快照、仓库、车辆、路线和目标权重，生成极速直送、成本集约和韧性均衡三套候选方案。每套方案包含仓库、安置点、物资、数量、路线、ETA、车辆趟次、重量和成本。库存分配不得超过去锁定后的可用数量；车辆趟次按货物总重量和最大载重计算。该 Agent 不能直接修改库存，也不能将方案标记为已核验。

4.4 独立核验智能体 A03

核验智能体采用隔离上下文，只读取原始需求、候选方案、原始库存、路线、车辆、事件封闭清单和规则库。它不读取匹配智能体的内部推理，也没有编辑方案的权限。核验包括道路封闭、库存不足、需求缺口、车辆趟次、时效和安全条件。发现硬阻断时输出 rework，并生成结构化问题代码、证据和修正要求。通过门槛为无硬阻断且评分不低于 80。

4.5 方案交付智能体 A04

交付智能体只消费通过核验的方案和核验报告。它生成推荐方案、备选方案、成本与时效对比、风险提示、执行清单、时间线和数据依据。它不能修改数字、删除风险，也不能绕过人工审批。若资源约束无法修复或达到三轮上限仍未通过，交付智能体只能输出转人工研判提示。

五、工作流编排设计

5.1 DAG 主链路

事件确认后进入并行入口。需求研判与 RAG 检索可并行执行，随后进入资源匹配、独立核验、条件判断、人工审批和方案交付。不同节点之间传递的是结构化产物，而不是自然语言长文本。这样既能支持可视化展示，也能在失败时准确定位是哪一个节点产生了问题。

5.2 并行分支

在应急场景中，规则检索和需求理解并不存在强依赖关系，可以并行执行。并行分支减少了首轮等待时间，也使平台具备真实 DAG 编排能力。前端设计器支持用 JSON 定义顺序、并行、条件节点、重试和子工作流，并提供“保存并试运行”按钮；试运行会真实写入 workflow_runs 与 workflow_node_runs，返回节点执行顺序、峰值并发和端到端耗时。

5.3 条件分支与人工门控

核验后根据 verdict 进入不同分支。pass 进入人工审批，rework 返回匹配智能体；系统按问题代码选择不同修复策略，达到三轮上限或资源约束无法自动修复时进入人工研判。人工审批是工作流中的正式节点，不是装饰按钮。只有审批通过后，报告才可进入执行准备状态。

5.4 回环设计

回环不是简单重试，而是带反馈的修正过程。核验智能体将问题压缩为问题代码、证据和修正要求，匹配智能体在第二轮排除封闭路线并重新计算库存和车辆。回环有最大次数，避免无限循环；当信息不足以修正时，系统明确升级为人工介入。

六、动态调度引擎设计

调度引擎读取事件等级、需求种类、受影响人口和封闭路线数量，计算任务复杂度，并基于角色能力、任务依赖和安全等级形成优先级。需求研判和 RAG 检索进入并行批次；资源匹配进入顺序批次；独立核验使用最高优先级并进行门控；交付节点必须在人工审批后执行。

调度器现在不仅展示优先级，还通过真实的 asyncio.PriorityQueue 执行 AgentArts 调用：每次运行使用 3 个异步 Worker，并记录每个任务的排队时间、执行时间、峰值并发和成功率。需求节点单独执行；资源匹配与独立核验可同时占用两个 Worker；交付节点在核验完成后进入队列。运行页和评估页读取这些真实指标，而不是只看到静态调度图。

七、自我循环与反馈优化

本项目的 Self-Loop 由“生成—验证—反馈—修正—再验证”组成。第一轮方案允许在规划阶段使用主通道，但独立核验读取事件封闭清单后会发现多个主通道不可通行。核验报告输出 7 类硬阻断，系统触发退回。第二轮回环中，匹配智能体排除封闭路线，使用备用通道并重新计算车辆趟次和成本。第二轮核验通过后，交付智能体只使用通过核验的事实。

系统输出闭环指标，包括尝试轮次、首轮评分、最终评分、评分提升、首轮阻断数量、最终阻断数量、排除封闭路线数和是否收敛。基准场景中，首轮评分 0 分，最终评分 100 分，评分提升 100 分，需求覆盖率 100%。这些指标不是为了美化结果，而是为了证明反馈循环确实改变了方案质量。

八、结果验证与可信机制

8.1 确定性规则优先

安全相关判断不能只依赖模型。库存、载重、ETA、道路封闭和需求覆盖均由确定性代码计算。LLM 可以解释为什么有问题，但不能把硬阻断改成通过，也不能修补库存数字。这样既保留了智能体的自然语言能力，又避免了关键计算被幻觉污染。

8.2 隔离核验

核验智能体的上下文与生成智能体隔离，只读取原始数据和最终候选方案。它没有编辑权限，只能返回通过、退回或人工介入。核验结果保留问题代码、证据引用和修正要求，支持复核和交叉验证。

8.3 人工审批

核验通过不等于可以自动执行。平台要求人工审批节点，记录审批时间和意见。原型中的执行准备是模拟状态，不发送真实调度命令。这条边界既符合应急管理责任体系，也避免原型夸大能力。

8.4 可复现

每次运行冻结库存快照，保存请求、Agent 事件、方案版本和核验报告。相同快照和规则下重复计算，结果应一致。评估接口会执行重复基准并比较阻断清单和通过方案 ID，验证方案不是随机生成。

九、RAG、知识库与记忆

9.1 知识库设计

原型包含需求测算、汛期道路封闭、多仓库存分配、车辆载重、PDCA 核验和交付字段六类规则文档。每条文档有编号、类别、关键词、来源和更新时间。检索使用中文二元组与关键词混合打分，返回 Top-K 证据片段。Agent 在输出中保留证据编号，前端在核验页展示证据标题、摘要和相似度。

9.2 为什么使用混合检索

纯向量检索在短规则和专有名词上可能出现语义偏移，纯关键词检索又无法覆盖表述差异。原型使用中文二元组和关键词混合检索，在本地可运行、可解释、无外部依赖。生产环境可替换为 AgentArts 知识库、Elasticsearch 或向量数据库，同时保留引用编号和更新时间。

9.3 记忆管理

系统记忆分为运行内黑board和跨运行审计记录。运行内记忆只保留当前任务所需的产物版本，避免无关上下文干扰；跨运行记忆保存运行编号、Agent 事件、方案版本和审批状态，用于审计和回放。Agent 不允许无限制累积对话历史。

十、LLM、AgentArts 与工具调用

10.1 LLM 定位

LLM/AgentArts 是 Agent 的理解、规划和表达核心，但安全关键数字由工具计算。需求智能体使用 LLM 理解非结构化灾情和用户意图；匹配智能体使用 LLM 解释多目标权衡和重规划理由；核验智能体使用 LLM 归纳问题根因，但结论受确定性规则约束；交付智能体使用 LLM 组织执行摘要和风险提示。

10.2 AgentArts 适配

后端提供 AgentArtsBridge，通过环境变量配置 Base URL、API Key、Agent 映射和调用路径。默认本地模式保证断网演示稳定，配置后可将同一结构化产物发送到 AgentArts Agent 进行推理和解释。四个 Agent 的配置参考位于 backend/agentarts/agents.json。

10.3 工具与协议

平台注册了库存查询、路线查询、多目标规划、规则引擎和 RAG 检索等工具，并以 Function Calling/MCP 风格暴露名称、协议、读写模式与说明。Agent 工具权限采用白名单模式：需求智能体不能查询库存分配；匹配智能体不能写库存；核验智能体不能修改方案；交付智能体只能读取已核验产物。

十一、物资库与库存数据

物资库解决“有哪些物资”，库存快照解决“某个仓库里有多少”。物资库保存物资编码、名称、别名、分类、规格、基本单位、包装单位、换算率、储存条件、保质期、冷链、危险品、单件重量和默认优先级。库存上传通过物资编码关联主数据，避免名称重复和单位混用。

每次库存上传都会形成独立快照，并记录上传时间、来源、记录数和状态。后续上传不会修改历史运行使用的数据版本。这样既支持数据更新，也能保证历史方案可复现。系统提供 CSV 和 XLSX 导入，校验仓库、物资、数量、有效期和状态，并输出错误与警告。

十二、核心页面与交互

调度工作台左侧是场景和需求配置，中间使用 Leaflet + 高德兼容瓦片展示真实地理态势、候选方案和交付结果，右侧是 Agent 状态和实时事件。物资选择器直接读取物资库，并显示当前库存。权重滑块允许用户调整时效、成本和安全的偏好，重新生成方案。

Agent 编排中心展示五个核心模块、四个 Agent 契约、工具注册、知识库和工作流画布。评估中心展示硬阻断拦截、核验评分提升、重复复现、需求覆盖和赛题能力矩阵。物资库、库存数据和运行记录页面分别承担主数据维护、快照上传和审计回放。

十三、测试、评估与性能

13.1 自动化测试

项目提供后端自动化测试。引擎测试覆盖固定场景下的自适应多轮核验闭环、问题分类策略和运力不足硬阻断；调度测试覆盖优先队列与并发指标；API 测试覆盖健康检查、物资库、场景读取、运行创建、状态轮询、结果验证、并发诊断和人工审批。测试运行命令为 cd backend && pytest -q。当前测试结果为 38 项通过。

13.2 基准评估

评估接口使用同一库存快照重复执行完整自适应求解，比较各轮的阻断清单、最终通过方案和运行指标是否一致。返回指标包括硬阻断数量、不安全方案拦截率、首轮评分、最终评分、评分提升、需求覆盖率、通过方案数、纯计算耗时、P95 和重复计算一致性。

固定场景结果如下：

  • 硬阻断发现：7 类；
  • 不安全方案拦截：3/3；
  • 首轮评分：0；
  • 最终评分：100；
  • 评分提升：100；
  • 最终需求覆盖：100%；
  • 通过方案：3 套；
  • 重复计算：结果一致；
  • 纯计算耗时：约 1 毫秒。

上述数据为模拟场景基准，不代表真实灾害条件下的行业准确率。它的作用是证明验证闭环、重算和可复现能力确实运行，而不是用模型输出替代测试。

13.3 性能目标

现场演示目标是在 20–40 秒内完成从事件到交付的完整体验，其中大部分时间为可视化节奏和 SSE 事件展示，确定性规划计算本身不到数毫秒。生产环境中影响性能的主要因素将是知识库检索、外部 LLM 调用、真实路网查询和并发任务数，因此后续需要增加缓存、超时、熔断、任务队列和并发压测。

十四、创新点

14.1 独立核验而非自评

平台把生成和核验拆成两个角色，核验角色使用隔离上下文和只读工具，不允许修改方案。这样可以避免“自己生成、自己批准”的确认偏差。该设计直接回应了赛题中“验证与可信机制缺失”的产业痛点。

14.2 结构化反馈驱动重算

核验失败时，系统不把整段自然语言报告丢回生成智能体，而是传递问题代码、证据和修正要求。下一轮匹配根据问题类别切换路线、库存分配、运力选择和时效目标，只修改受影响约束；如果资源总量确实不足，则直接转人工研判。

14.3 数据快照与可复现运行

每次库存上传形成独立快照，每次推演固定引用快照。历史运行不会因为后续上传而改变，重复计算能够对比通过方案和阻断清单。这对应急演练、复盘和答辩质询非常重要。

14.4 确定性工具与智能体协作结合

系统没有让大模型直接“猜库存”或“算 ETA”，而是将确定性工具和 LLM 放在各自擅长的位置。Agent 做理解、协调和解释，规则引擎做硬判断，人工做最终责任确认。这样的职责边界比单纯追求全自动更符合真实行业落地。

14.5 可视化编排

Agent 编排中心把角色定义、工具权限、工作流、并行分支、条件判断和回环集中呈现，便于评委在短时间内理解系统不是四个提示词的简单串联，而是一个可视化的多 Agent Harness。

十五、工程化与部署

15.1 代码结构

后端按配置、模型、数据库、工具、Agent、编排、评估和 API 分层。前端按页面、组件、API 客户端和全局样式分层。AgentArts 适配、知识库、调度器和评估模块相互独立，便于替换和扩展。

15.2 部署方式

默认启动项目内 PostgreSQL 18、FastAPI 和前端静态资源。执行 start.cmd 可自动构建前端、启动数据库并启动服务，浏览器访问 http://127.0.0.1:8000。正式部署可使用 Docker Compose + RDS/GaussDB。开发模式可分别启动 FastAPI 和 Vite，前端通过代理访问 API。

15.3 异常处理

系统对不存在的场景、无效物资、库存文件缺列、仓库引用错误、物资未匹配、重复物资、审批状态错误和 Agent 调用异常均有处理。核验失败不会导致系统崩溃，而是进入重算或人工研判。AgentArts/LLM 不可用时回退到本地确定性模式，保证演示可继续。

15.4 可扩展性

当前正式运行时已使用 PostgreSQL，并接入真实地图底图；后续可将知识检索升级为 AgentArts 知识库或向量数据库，将路线升级为授权路径规划 API，将车辆查询替换为物流平台接口，并将执行监控接入消息队列和审计中心。四个 Agent 的输入输出契约保持不变，便于逐步替换运行时。

十六、数据安全与隐私保护

当前原型不接入真实个人身份、医疗和位置数据，只使用演练物资、仓库和安置点信息。生产部署建议采取以下措施：

  1. 物资库和库存上传使用角色权限控制，操作员不能修改核验规则；
  2. API Key 和 AgentArts 密钥仅保存在服务端环境变量；
  3. 运行记录按项目和租户隔离；
  4. 库存、道路和车辆数据按敏感等级分类，真实储备库位置不对外公开；
  5. 所有上传、审批和导出操作写入审计日志；
  6. 导入文件进行类型、大小、行数和字段校验；
  7. 生产环境使用 HTTPS、数据库加密和备份恢复；
  8. LLM/AgentArts 调用前对敏感字段进行脱敏，并保留数据使用说明。

十七、落地路径

第一阶段是演练与预案编制。用户上传内部物资和车辆数据，用平台生成不同灾害等级下的调度草案，发现资源缺口和道路依赖。

第二阶段是合作验证。与园区、学校、医院或物流企业联合，使用经过授权的内部数据进行演练，记录响应时间、方案采纳率、人工修改比例和缺口发现数量。

第三阶段是系统集成。接入企业 WMS/ERP、车队定位、地图路况和应急指挥平台，增加单点登录、权限、审计、消息队列和高可用部署。

第四阶段是行业模板。沉淀学校、医院、园区、社区和物流企业不同的 Agent 配置、核验规则和报告模板，形成可复制的应急调度工作流产品。

十八、局限与风险说明

  1. 当前事件、库存和路网为模拟数据，不能代表真实灾害现场。
  2. 当前原型不自动发现灾害，事件必须由用户或外部系统确认。
  3. 当前不直接控制真实车辆、仓库和物资，执行仍需人工。
  4. LLM/AgentArts 未配置时使用本地确定性回退，AI 生成能力有限。
  5. 规则库仍需行业专家审核，生产使用前必须经过安全评估。
  6. 多仓多车型多需求点的完整车辆路径问题是 NP-Hard，原型采用简化约束和启发式方案，生产环境需进一步优化求解器和并发架构。
  7. 系统不替代应急指挥人员的判断和责任。

十九、人工智能使用说明

项目中的 AI 使用遵循“AI 负责理解与协调、工具负责计算、规则负责核验、人类负责最终决策”的原则。

LLM/AgentArts 的作用包括：理解非结构化事件描述、归纳需求假设、解释多目标权衡、组织核验问题根因、生成交付摘要和风险提示。它们不直接决定库存数量，不直接计算路线时间，不直接修改方案，也不直接批准交付。

RAG 的作用是检索需求测算、道路封闭、库存分配、车辆载重、核验和交付规则，并为输出提供证据编号。工具调用的作用是查询库存、路线、车辆和规则。确定性规则引擎的作用是执行硬约束检查。人工审批的作用是承担最终责任。

这种分工的局限性是：没有 LLM 时，系统仍可完成确定性调度演示，但自然语言理解和解释能力会下降；没有真实数据时，系统只能验证算法和交互，不能证明真实行业准确率；没有专业人员审核时，规则库不能直接用于生产。

二十、结论

急先锋把多智能体编排从“四个提示词依次调用”推进到“有角色定义、有工具权限、有并行分支、有条件判断、有独立核验、有反馈回环、有版本快照、有人工审批”的可运行平台原型。它既能在断网环境稳定演示，又为 AgentArts、LLM、RAG 和真实行业数据保留了标准接入点。

项目最值得展示的不是某一个页面，而是第一轮方案被独立核验发现道路封闭、随后通过结构化反馈改用备用通道并重新通过核验的过程。这个过程同时证明了多 Agent 协作、动态调度、结果验证、自我循环和可复现工程能力，与赛道一的评分重点直接对应。
